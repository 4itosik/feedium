# FT-013: Post Embedding Persistence

## What

Выбран `large.md`. Rationale: фича вводит новую схему БД (`post_embedding`) и goose-миграцию, новый внутренний контракт переиспользования/инвалидации вектора и новый enqueue-путь переоценки на scoring-outbox, реверсирует ADR-gated инвариант хранения векторов (ADR-001 `DEC-02`/`NS-05`) и потому зависит от нового `ADR-002`, требует явных `ASM-*`/`CON-*`/`DEC-*`/`INV-*`/`CTR-*`/`FM-*` и нескольких acceptance scenarios (переиспользование, инвалидация по тексту, согласованность модели, авто-переоценка при смене интересов, сохранность поведения FT-010) с несколькими `CHK-*`/`EVID-*`. Любое из этих условий уже исключает `short.md` ([feature-flow.md §Выбор шаблона](../../flows/feature-flow.md#выбор-шаблона-featuremd)).

### Problem

FT-010 оценивает релевантность так: для каждого поста его саммари **эмбеддится через внешний AI-сервис заново при каждом скоринге**, вектор используется для косинуса и **выбрасывается** — `ScorePost` зовёт `uc.scorer.Embed(ctx, summaries[0].Text)` и не сохраняет результат ([`internal/biz/score.go:201`](../../../internal/biz/score.go)). Кешируются только эмбеддинги интересов (`Interest.embedding JSONB`, FT-010 `DEC-04`, [`migrations/20260602100000_create_interests_table.sql:5`](../../../migrations/20260602100000_create_interests_table.sql)); вектор поста — самый дорогой и самый переиспользуемый артефакт пайплайна — каждый раз вычисляется с нуля.

Это feature-specific delta относительно зафиксированного в [FT-010 feature.md](../FT-010-ai-scoring/feature.md): метод и формат оценки не меняются, меняется только жизненный цикл пост-вектора (транзиентный → персистентный) и распространение смены интересов на оценку.

Последствия бездействия (детали и метрики — в [`brief.md`](brief.md)):

- **Платный вызов на каждую переоценку.** Повторная оценка поста (например, после смены интересов) = один оплачиваемый embedding-запрос на пост, хотя текст не менялся и вектор был бы тем же; на ленте из N постов это N лишних платных вызовов (`RISK-02`/`RISK-05`, [PRD-001 → Risks](../../prd/PRD-001-mvp.md#risks-and-open-questions)).
- **Экономика не сходится на потоке PRD-001:** при потоке до 10 000 постов/день и цикле подстройки интересов стоимость растёт по числу переоценок, а не по числу нового контента.
- **Добавочная задержка** на сетевой embed при каждой переоценке нагружает сквозной бюджет `MET-03` (< 5 минут).
- **Связь «смена интересов → видимый эффект» дорогая:** acceptance FT-010 «изменения интересов наблюдаемо влияют на оценку» достижим сегодня только ценой полного повторного эмбеддинга затронутых постов.

Обнаружено при e2e-проверке пайплайна 2026-06-07: скоринг работает, но `ScorePost` эмбеддит саммари на каждом вызове и не сохраняет результат.

### Outcome

Метрики FT-013 — объективно проверяемые feature-local outcomes об устранении повторного embed. Project-level пороги `MET-03` (задержка < 5 мин) и экономика провайдера (`RISK-02`/`RISK-05`) определены upstream; FT-013 обязан их улучшать и не ломать, но не поднимает их как собственный KPI (`NS-08`).

| Metric ID | Metric | Baseline | Target | Measurement method |
| --- | --- | --- | --- | --- |
| `MET-01` | Платные embed-вызовы при переоценке поста с неизменным входным текстом и моделью | 1 embed на пост на каждую переоценку (`score.go:201`) | 0 embed-вызовов при неизменных (текст, модель) | Интеграционный тест: повторный `ScorePost` того же поста → `Scorer.Embed` не вызывается (счётчик мока/провайдера) |
| `MET-02` | Платные embed-вызовы при переоценке ленты из N постов после смены набора интересов | N embed (по числу постов) | 0 новых embed при неизменных текстах постов | Тест на testcontainers: смена интереса → авто-переоценка существующих постов → 0 исходящих `Embed` |
| `MET-03` | Сохранность наблюдаемого поведения FT-010 при включённом переиспользовании | N/A (вектор транзиентен) | Значения оценок и «ровно одна актуальная оценка на пост» идентичны вычислению с нуля | Дифф-тест: оценка через переиспользуемый vs пересчитанный вектор для тех же (текст, модель, интересы) совпадает |

### Scope

- `REQ-01` После первой оценки поста его эмбеддинг сохраняется и переиспользуется при последующих оценках того же поста **без нового вызова AI-сервиса**, пока входной текст саммари и embedding-модель неизменны.
- `REQ-02` При изменении входного текста поста (саммари) сохранённый вектор признаётся неактуальным и пересчитывается; оценка считается по новому вектору.
- `REQ-03` Согласованность модели: оценка **никогда** не считает косинус между векторами, полученными разными embedding-моделями; смена модели делает сохранённый вектор поста неактуальным (пересчёт) и наблюдаема; рассогласование обрабатывается без молчаливо неверной оценки.
- `REQ-04` Изменение набора интересов (создание, изменение, удаление интереса) **автоматически ставит в очередь переоценку** существующих оценённых постов; переоценка переиспользует сохранённые векторы и не обращается к AI-сервису при неизменных текстах.
- `REQ-05` Наблюдаемое поведение скоринга и ранжирования FT-010 — значения оценок, инвариант «ровно одна актуальная оценка на пост», устойчивость к сбою AI — сохраняется при включённом переиспользовании вектора.
- `REQ-06` Хранение вектора поста остаётся в рамках PostgreSQL-инфраструктуры MVP: Docker-образ `postgres:18.3-alpine` неизменен, без расширений БД (`CREATE EXTENSION`/pgvector).
- `REQ-07` Переиспользование и инвалидация вектора покрыты автотестами согласно [testing-policy](../../engineering/testing-policy.md).

### Non-Scope

- `NS-01` Изменение самого метода скоринга, выбора embedding-модели или формулы релевантности — зафиксированы в FT-010 / [`ADR-001`](../../adr/ADR-001-scoring-method-and-vector-storage.md) и не трогаются.
- `NS-02` Поиск похожих постов, семантический поиск и дедупликация на основе сохранённых векторов — потенциальные downstream-возможности, не входят сюда.
- `NS-03` Массовый разовый бэкафилл векторов всей исторической ленты как отдельная продуктовая операция: вектор вычисляется **лениво** по факту оценки/переоценки поста, а не пакетным проходом по архиву.
- `NS-04` Пользовательский интерфейс (FT-011) и Telegram-бот OpenClaw (FT-012).
- `NS-05` Введение pgvector, внешнего vector-store или ANN-поиска — остаётся отвергнутым (`ADR-001 DEC-02`, подтверждается `ADR-002`).
- `NS-06` Ретеншн/прунинг/эвикция сохранённых векторов как фича — отмечается как follow-up в `ADR-002` (вектор — кэш, безопасен к удалению), но в FT-013 не реализуется.
- `NS-07` Изменение механики FT-005 (суммаризация) и FT-007 (generic event-processing: lease/retry/reaper) — переиспользуются как есть; FT-013 лишь добавляет новый enqueue-путь на **scoring**-outbox FT-010.
- `NS-08` Подъём или переопределение project-level порогов `MET-03` PRD-001 как собственного KPI FT-013.

### Constraints / Assumptions

- `ASM-01` У поста есть `Summary` (FT-005, [`internal/ent/schema/summary.go`](../../../internal/ent/schema/summary.go)); входной текст эмбеддинга — `summaries[0].Text`, как в текущем `ScorePost` ([`score.go:185-201`](../../../internal/biz/score.go)). FT-013 не меняет выбор входного текста.
- `ASM-02` Кэш эмбеддингов интересов (FT-010 `DEC-04`, `Interest.embedding []float32` как JSONB) уже существует; пост-вектор хранится **тем же способом** (JSONB, косинус в `biz/`).
- `ASM-03` Существует scoring-outbox с pull-моделью, атомарным захватом, lease, retry и санацией (`ScoreOutboxRepo`, [`internal/biz/score_outbox.go`](../../../internal/biz/score_outbox.go); reaper в [`score.go:150`](../../../internal/biz/score.go)) — это референс-паттерн для постановки переоценки в очередь.
- `ASM-04` Пользователь один, набор интересов глобален для инстанса ([problem.md → Product Context](../../domain/problem.md#product-context), `PCON-01`); смена интересов — основной рабочий цикл, где переоценка происходит массово.
- `CON-01` PostgreSQL-only: образ `postgres:18.3-alpine` ([`docker-compose.yml:3`](../../../docker-compose.yml), [`docker-compose.prod.yml:14`](../../../docker-compose.prod.yml)) неизменен; без `CREATE EXTENSION`/pgvector. Вектор хранится как JSONB, косинус считается в `biz/` (`Cosine`/`Relevance`, [`score.go:38-83`](../../../internal/biz/score.go)) — как для интересов сегодня.
- `CON-02` Переиспользование вектора не ослабляет инвариант FT-010 «ровно одна актуальная оценка на пост» (`UNIQUE(post_id)` на `scores`, [`internal/ent/schema/score.go:48`](../../../internal/ent/schema/score.go)) и устойчивость к сбою AI.
- `CON-03` Вектор поста хранится как **отдельная связанная сущность**; схема `posts` FT-004 ([`internal/ent/schema/post.go`](../../../internal/ent/schema/post.go)) структурно не меняется — как `scores` сегодня (FT-010 `CTR-06`).
- `CON-04` Стоимость и латентность внешнего AI-сервиса (`RISK-02`/`RISK-05`) — доминирующий драйвер; цель фичи — снять повторный, избыточный embed.
- `DEC-01` Способ и форма хранения вектора, его формат, момент вычисления, сигнал инвалидации при изменении текста, обработка смены embedding-модели и механика авто-переоценки при смене интересов фиксируются в [`ADR-002`](../../adr/ADR-002-post-embedding-persistence.md) (`decision_status: proposed`). Пока `ADR-002` не переведён в `accepted`, эти решения **не считаются finalized design**; `feature.md` не переходит на Plan Ready (ADR-gate, см. `§ADR Dependencies`).

### Invariants

- `INV-01` Косинус считается только между векторами **одной** embedding-модели. Кросс-модельный косинус запрещён; при рассогласовании модели пост-вектора и интерес-векторов оценка завершается наблюдаемо (`ErrScoreValidation`/метрика), а не молчаливо неверным значением (`REQ-03`).
- `INV-02` Сохранённый вектор поста актуален **тогда и только тогда**, когда его `input_hash` и `model` совпадают с текущими (хеш текущего входного текста и текущая модель скоринга); иначе вектор пересчитывается и перезаписывается (`REQ-01`, `REQ-02`, `REQ-03`).
- `INV-03` Вектор поста — производный кэш: он всегда восстановим из текста саммари. Его отсутствие/удаление не теряет данных, а лишь требует повторного embed при следующей оценке (обосновывает `NS-06` и mitigation роста БД).
- `INV-04` (наследуется из FT-010) у поста ровно одна актуальная оценка; переиспользование вектора не создаёт второй актуальной записи (`CON-02`).

## How

### Solution

Ввести новую связанную сущность `PostEmbedding` в рамках PostgreSQL — ровно один сохранённый вектор на пост (1:1, `UNIQUE(post_id)`), хранящий сам вектор как JSONB плюс `model` и `input_hash` входного текста. `ScorePost` перед обращением к провайдеру проверяет сохранённый вектор: если `input_hash` и `model` совпадают с текущими — переиспользует его и **не зовёт** `Scorer.Embed`; иначе вычисляет эмбеддинг, перезаписывает сохранённый вектор и считает релевантность. Согласованность модели обеспечивается guard-ом в `biz/`: косинус между векторами разных моделей не считается, рассогласование — наблюдаемая терминальная ошибка. Смена набора интересов (`InterestUsecase.Create/Update/Delete`, [`internal/biz/interest.go:84-132`](../../../internal/biz/interest.go)) добавляет на scoring-outbox новый enqueue-путь переоценки существующих оценённых постов, которые переиспользуют сохранённые векторы. Главный trade-off: сознательно принимаем рост объёма БД (то, чего ADR-001 избегал) в обмен на устранение повторного платного embed — вектор это кэш, безопасный к будущему прунингу.

Конкретные форма таблицы, тип/размерность хеша, момент и место guard-а, форма enqueue-запроса переоценки и батчинг — фиксируются `ADR-002` и детализируются в sibling [`implementation-plan.md`](implementation-plan.md) (после перевода `ADR-002` в `accepted`).

### Flow

1. **Вход.** Событие скоринга поста (`ScoreEvent`, [`score_outbox.go:24`](../../../internal/biz/score_outbox.go)) — от первичной оценки (FT-010) или от авто-переоценки при смене интересов (`REQ-04`); пост с завершённым `Summary` (`ASM-01`) и текущий набор `Interest` с их моделью.
2. **Обработка.** `ScorePost` читает саммари и вычисляет `input_hash` входного текста. Если есть сохранённый `PostEmbedding` с совпадающими `input_hash` и `model` (`INV-02`) — вектор переиспользуется **без** вызова `Scorer.Embed` (`REQ-01`). Иначе вектор вычисляется через провайдера, сохранённый вектор перезаписывается (`REQ-02`/`REQ-03`). Перед косинусом guard проверяет согласованность модели пост-вектора и интерес-векторов; рассогласование → `ErrScoreValidation` наблюдаемо (`INV-01`, `CTR-04`). Релевантность считается max-косинусом (`Relevance`, без изменений) и upsert-ится как одна актуальная оценка (`INV-04`).
3. **Выход.** У поста — одна актуальная оценка и один сохранённый актуальный вектор. Повторная оценка того же поста (неизменный текст/модель) не порождает исходящего embed-вызова (`MET-01`). Смена набора интересов наблюдаемо переоценивает существующие посты за счёт сохранённых векторов, без новых платных embed при неизменных текстах (`REQ-04`, `MET-02`).

### Failure Modes

- `FM-01` **AI-сервис недоступен при первом вычислении или пересчёте вектора** (timeout/5xx, `RISK-05`). Событие скоринга возвращается в очередь с backoff до терминального завершения (наследует FT-010 `FM-01`, `IsTransientScoreError` [`score.go:88`](../../../internal/biz/score.go)); сохранённого/частичного вектора не остаётся, пост не оценивается молча неверно.
- `FM-02` **Сохранённый вектор повреждён или его размерность не совпадает с интерес-векторами.** `Cosine` возвращает `ErrScoreValidation` (terminal, наблюдаемо, [`score.go:42`](../../../internal/biz/score.go)); пост не теряется, оценка не считается молча.
- `FM-03` **Смена embedding-модели (config).** Сохранённые пост-векторы с прежней моделью неактуальны (`INV-02`): пересчёт под текущую модель при следующей оценке; косинус между разными моделями не считается (`INV-01`, `CTR-04`); смена наблюдаема (лог/метрика).
- `FM-04` **Параллельная переоценка одного поста при смене интересов.** Partial unique index не даёт второй активный `score_event`; upsert вектора и оценки идемпотентны (наследует FT-010 `FM-03`/`FM-04`, `INV-04`).
- `FM-05` **Рост объёма БД из-за хранения векторов** (причина отказа в ADR-001). Принят сознательно: экономия повторного embed доминирует, объём ограничен числом постов, а не числом переоценок; вектор — кэш, прунинг доступен как follow-up (`NS-06`, `INV-03`, `ADR-002`).
- `FM-06` **Всплеск нагрузки на scoring-outbox при смене интересов** (массовая постановка переоценки). Поглощается существующими lease/retry/конкурентностью FT-007; throttle/батч — деталь плана, не меняет инварианты (`CTR-03`).

## Verify

`Verify` задаёт canonical test case inventory FT-013: positive scenarios через `SC-*`, negative/edge через `NEG-*`, executable checks через `CHK-*` и evidence через `EVID-*`.

### Exit Criteria

- `EC-01` Повторная оценка поста с неизменными `(текст, модель)` не вызывает `Scorer.Embed` (наблюдаемо).
- `EC-02` Изменение входного текста саммари приводит к пересчёту вектора и оценке по новому вектору.
- `EC-03` Смена набора интересов переоценивает существующие оценённые посты без новых embed при неизменных текстах.
- `EC-04` Косинус между векторами разных embedding-моделей никогда не считается; рассогласование наблюдаемо и не даёт молчаливо неверной оценки.
- `EC-05` Инвариант «ровно одна актуальная оценка на пост», значения оценок и устойчивость к сбою AI сохраняются при включённом переиспользовании.
- `EC-06` Образ `postgres:18.3-alpine` неизменен, без расширений; вектор хранится как JSONB, миграция применяется на чистой БД.

### Acceptance Scenarios

- `SC-01` **Переиспользование (happy path).** Пост оценён → вектор сохранён. Повторная оценка того же поста с неизменным текстом и моделью → 0 вызовов `Embed`, та же оценка.
- `SC-02` **Инвалидация по тексту.** Текст саммари поста изменился → при следующей оценке вектор пересчитан (ровно 1 `Embed`), сохранённый вектор перезаписан, оценка считается по новому вектору.
- `SC-03` **Авто-переоценка при смене интересов.** Существуют оценённые посты с сохранёнными векторами → создание/изменение/удаление интереса ставит их в очередь переоценки → посты переоценены, 0 новых `Embed` при неизменных текстах, актуальные оценки обновлены.
- `SC-04` **Согласованность модели.** Сохранённый вектор от модели A, текущая модель B → вектор пересчитан под B; косинус A×B не считается; смена модели наблюдаема.
- `SC-05` **Сохранность FT-010.** При включённом переиспользовании: ровно одна актуальная оценка на пост; transient-сбой AI обрабатывается как в FT-010; значения оценок совпадают с вычислением «с нуля» для тех же входов (`CTR-05`).

### Negative / Edge

- `NEG-01` Сохранённый вектор повреждён / рассогласован по размерности или модели → `ErrScoreValidation` (terminal, наблюдаемо), пост не теряется, молчаливо неверная оценка не пишется (`FM-02`/`FM-03`).
- `NEG-02` AI-сервис недоступен при пересчёте вектора → transient retry; частичная или молчаливая запись неверной оценки не происходит (`FM-01`).
