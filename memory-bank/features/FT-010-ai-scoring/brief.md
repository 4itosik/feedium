# FT-010: AI Scoring & Ranking

## Problem

Пайплайн уже собирает (FT-009) и суммаризирует (FT-005) контент, но отдаёт его **в порядке поступления, без ранжирования по интересам**. Главная боль продукта остаётся нерешённой: при 10+ источниках 80%+ потока — нерелевантный шум, и пользователь по-прежнему вынужден глазами отделять нужное от лишнего.

Последствия бездействия:

- Недостижим целевой outcome PRD-001 `MET-04` («доля релевантного в топ-20 > 70%»): без скоринга у ленты нет понятия «топ» — все посты равны и выстроены по времени, а не по ценности.
- Текущее состояние воспроизводит исходную боль: вместо ручного обхода источников пользователь делает ручную фильтрацию единой, но неотсортированной ленты — work не убран, а перемещён.
- Простаивает уже построенная цепочка: собранный и просуммированный контент некому ранжировать, поэтому ценность FT-009/FT-005 не конвертируется в «открыл — увидел главное».
- Блокируются downstream-фичи доставки: и React UI (FT-011), и дайджест OpenClaw (FT-012) опираются на наличие порядка по релевантности; без него им нечего показывать «сверху».
- Остаётся открытым `OQ-01` PRD-001: подход к скорингу/ранжированию не зафиксирован, и продукт не может закрыть свою North Star («перестать ходить в источники руками»).

## Task

Присваивать каждому посту **оценку релевантности относительно интересов пользователя** и давать возможность получить **ленту, отсортированную по этой оценке**, — автоматически, без ручного запуска и без поломки сквозной задержки появления контента (`MET-03` PRD-001 < 5 минут).

1. Пользователь может задавать и менять **набор своих интересов**; система опирается на него при оценке.
2. Каждый просуммированный пост автоматически получает оценку релевантности — без ручного вызова со стороны пользователя.
3. Явно нерелевантный контент получает низшую оценку и оказывается в хвосте ленты, а не теряется.
4. Доступна выдача отранжированной ленты: посты в порядке убывания релевантности, с фильтрацией по времени и порогу.
5. Повторная оценка поста обновляет его оценку, а не порождает дубликаты; при параллельной обработке у поста ровно одна актуальная оценка.
6. Временная недоступность внешнего AI-сервиса не теряет пост из будущей ленты и наблюдаема.

Конкретный метод оценки (эмбеддинги, LLM-судья или их сочетание), выбор моделей, способ хранения и поиска векторов, пороги отсечения, формат оценки и механизм постановки оценки в очередь — задача Design-фазы (закрывает `OQ-01`).

## Context

- Разрабатывается MVP Feedium; FT-001..FT-009 обеспечивают каркас, хранилище, управление источниками и постами, суммаризацию и масштабируемую обработку событий. Скоринг — недостающее звено `collect → summarize → **score/rank** → deliver`.
- Пользователь системы один (см. [problem.md](../../domain/problem.md)); набор интересов глобален для инстанса, без понятия владельца и без мультипрофилей.
- Поводом служит то, что без ранжирования ни одна из фич доставки (React UI, OpenClaw) не имеет упорядоченного входа, а главный продуктовый outcome (`MET-04`) не измерим.
- Скоринг опирается на внешний платный AI-сервис с известными рисками PRD-001 (стоимость и доступность провайдера, `RISK-02`/`RISK-05`); Design обязан учесть экономику при потоке до 10 000 постов в день и деградацию при сбоях.
- Интересы — новая управляемая сущность; их жизненный цикл (создание/изменение/удаление) повторяет модель управления источниками (FT-003) и не вводит пользовательскую аутентификацию.

## Users

- **Пользователь Feedium** — вместо фильтрации неотсортированного потока получает ленту, где релевантное вверху; задаёт свои интересы и видит их влияние на порядок.

## Scope

### In Scope

- Пользовательское управление набором интересов (задать, посмотреть, изменить, удалить) через существующую поверхность API и feediumctl.
- Автоматическая оценка релевантности каждого просуммированного поста относительно интересов, без ручного запуска.
- Низшая оценка и попадание в хвост ленты для явно нерелевантного контента (без его удаления).
- Выдача отранжированной ленты: сортировка по релевантности по убыванию, фильтрация по времени и порогу, через API и feediumctl.
- Идемпотентность оценки: у поста ровно одна актуальная оценка; повторная обработка обновляет её и не создаёт дубликатов, в том числе при нескольких параллельных воркерах/процессах.
- Устойчивость к сбою внешнего AI-сервиса: пост не теряется из будущей ленты, ошибка наблюдаема.
- Хранение оценок и интересов остаётся в рамках PostgreSQL, как и вся инфраструктура MVP.
- Автотесты операций скоринга и выдачи ленты согласно testing-policy проекта.

### Out Of Scope

- Пользовательский интерфейс (React UI) — ранжированную ленту визуализирует FT-011; здесь только её программная выдача.
- Telegram-бот OpenClaw (FT-012).
- Обучение/файнтюнинг моделей и персонализация по обратной связи (лайки/дизлайки, обучение на поведении) — post-MVP-гипотезы (`OQ-03`/`OQ-04`).
- Тематическая классификация и дедупликация постов (`OQ-03`/`OQ-04`).
- Массовый пере-скоринг всей исторической ленты при изменении интересов: оцениваются посты по мере появления саммари.
- Мультипользовательские профили интересов и пользовательская аутентификация.
- Выбор метода оценки, моделей, способа хранения векторов, порогов и механизма очереди — задача Design-фазы.

## Acceptance Criteria

- Пользователь может задать интерес, увидеть список интересов, изменить и удалить интерес через API/feediumctl, и эти изменения наблюдаемо влияют на оценку постов.
- Просуммированный пост без ручного вмешательства получает оценку релевантности.
- Пост, явно не отвечающий интересам, получает низшую оценку и оказывается в хвосте отранжированной ленты, оставаясь доступным.
- Запрос отранжированной ленты возвращает посты по убыванию релевантности с корректной фильтрацией по времени и порогу.
- У каждого просуммированного поста ровно одна актуальная оценка; параллельная обработка несколькими воркерами не порождает дубликатов оценок.
- При недоступном AI-сервисе обработка поста повторяется и в итоге завершается терминально без зависания; пост не выпадает из будущей ленты, факт сбоя зафиксирован наблюдаемым образом.
- Операции скоринга и выдачи ленты покрыты автотестами согласно testing-policy проекта.

## Pre-existing Assets

- FT-003 — управление источниками: эталон CRUD-модели и поверхности API/feediumctl для новой управляемой сущности «интерес».
- FT-004 — управление постами: персистентное хранение постов, поля источника/даты/внешнего идентификатора.
- FT-005 — суммаризация: готовый `Summary` для поста — вход для оценки релевантности; outbox гарантирует запуск обработки.
- FT-007 — масштабируемая обработка событий: pull-модель воркеров, атомарный захват, lease, retry с backoff, graceful shutdown — референс-паттерн для автоматической оценки после саммари.
- FT-006 — feediumctl: read-only CLI поверх сервисов, точка расширения для управления интересами и просмотра ленты.
- [problem.md](../../domain/problem.md) — North Star, единственный пользователь, проблема шума 80%+, `MET-04`.
- [glossary.md](../../domain/glossary.md) — Source, Post, Summary, Score, режимы обработки.
- PRD-001 — `MET-04` (релевантность топ-20), `MET-03` (задержка < 5 мин), `OQ-01` (подход к скорингу не определён — закрывается этой фичей), `RISK-02`/`RISK-05` (поток и экономика AI-провайдера).
