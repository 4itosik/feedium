# FT-010-ai-scoring: AI Scoring & Ranking

## What

Выбран `large.md`. Rationale: фича вводит новые контракты API (управление интересами + выдача отранжированной ленты) и новую схему БД (интересы и оценки), добавляет новый config/env-контракт (внешний AI-сервис скоринга, параметры конкурентности/lease/retry/порога), опирается на внешнюю систему с известными рисками `RISK-01`/`RISK-02`/`RISK-05` и потому требует явных `ASM-*` / `CON-*` / `CTR-*` / `FM-*`, нескольких acceptance scenarios (CRUD интересов, авто-скоринг, ранжированная лента, идемпотентность, конкурентность, устойчивость к сбою AI, наблюдаемый эффект смены интересов) и нескольких `CHK-*` / `EVID-*`. Любое из этих условий уже исключает `short.md` ([feature-flow.md §Выбор шаблона](../../flows/feature-flow.md#выбор-шаблона-featuremd)).

### Problem

Пайплайн уже собирает (FT-009) и суммаризирует (FT-005) контент, но отдаёт его в порядке поступления, без ранжирования по интересам: ни одной сущности `Score`/`Interest` в схеме нет ([`internal/ent/schema/`](../../../internal/ent/schema/) содержит только `post.go`, `source.go`, `summary.go`, `summary_event.go`), нет ни API ленты, ни команды feediumctl для ранжированной выдачи ([`cmd/feediumctl/internal/app/`](../../../cmd/feediumctl/internal/app/) покрывает `health`/`source`/`post`/`summary`, но не feed/interest). Недостающее звено пайплайна `collect → summarize → score/rank → deliver` — скоринг и ранжирование ([`glossary.md → AI-скоринг / Ранжирование`](../../domain/glossary.md#ai-скоринг)).

Это feature-specific delta относительно [PRD-001](../../prd/PRD-001-mvp.md): общая постановка обогащения и ранжирования зафиксирована в [problem.md → Core Workflows `WF-02`](../../domain/problem.md#core-workflows); FT-010 закрывает конкретный недостающий шаг — авто-оценку каждого просуммированного поста и упорядоченную выдачу.

Последствия бездействия:

- Недостижим целевой outcome `MET-04` PRD-001 («доля релевантного в топ-20 > 70%», [problem.md → Outcomes](../../domain/problem.md#outcomes)): без скоринга у ленты нет понятия «топ» — все посты выстроены по времени, а не по ценности.
- Текущее состояние воспроизводит исходную боль (`MET-02`, [problem.md → Outcomes](../../domain/problem.md#outcomes)): вместо ручного обхода источников пользователь делает ручную фильтрацию единой, но неотсортированной ленты — work перемещён, а не убран.
- Простаивает уже построенная цепочка: собранный и просуммированный контент некому ранжировать, ценность FT-009/FT-005 не конвертируется в «открыл — увидел главное».
- Блокируются downstream-фичи доставки: React UI (FT-011) и дайджест OpenClaw (FT-012) опираются на наличие порядка по релевантности.
- Остаётся открытым `OQ-01` PRD-001 ([PRD-001 → Risks And Open Questions](../../prd/PRD-001-mvp.md#risks-and-open-questions)): подход к скорингу/ранжированию не зафиксирован.

### Outcome

Метрики FT-010 — объективно проверяемые feature-local outcomes. Subjective project-level пороги `MET-04` (релевантность топ-20 > 70%) и `MET-03` (задержка публикация → лента < 5 минут) определены в [problem.md → Outcomes](../../domain/problem.md#outcomes); FT-010 делает ранжирование возможным и обязан не ломать `MET-03` (`CON-04`), но не переопределяет и не поднимает эти пороги как собственный KPI (`NS-09`).

| Metric ID | Metric | Baseline | Target | Measurement method |
| --- | --- | --- | --- | --- |
| `MET-01` | Просуммированные посты, получающие оценку релевантности без ручного вызова | 0% (скоринга нет) | 100% просуммированных постов получают оценку автоматически | Интеграционный тест: завершение Summary → появление оценки у поста без вызова scoring-API |
| `MET-02` | Доступность отранжированной выдачи ленты | N/A (лента по времени, не по релевантности) | Лента возвращает посты по убыванию оценки с фильтрацией по времени и порогу | Интеграционный тест: выдача упорядочена по убыванию score, фильтры по времени и порогу применены |
| `MET-03` | Дубликаты актуальной оценки при параллельной обработке | N/A (скоринга нет) | 0 дубликатов актуальной оценки на пост при M процессов × N воркеров | Интеграционный тест на testcontainers: конкурентный скоринг одного набора постов, проверка 1 актуальная оценка на пост |

### Scope

- `REQ-01` Пользователь задаёт, просматривает, изменяет и удаляет набор своих интересов через существующую поверхность API и feediumctl; изменения набора интересов наблюдаемо влияют на оценку постов, оцениваемых после изменения.
- `REQ-02` Каждый просуммированный пост автоматически получает оценку релевантности относительно текущего набора интересов — без ручного вызова со стороны пользователя.
- `REQ-03` Явно нерелевантный контент получает низшую оценку и оказывается в хвосте отранжированной ленты, оставаясь доступным (не удаляется).
- `REQ-04` Доступна выдача отранжированной ленты через API и feediumctl: посты в порядке убывания оценки, с фильтрацией по времени и по порогу оценки.
- `REQ-05` У каждого просуммированного поста ровно одна актуальная оценка: повторная оценка обновляет её и не порождает дубликатов, в том числе при нескольких параллельных воркерах/процессах.
- `REQ-06` Временная недоступность внешнего AI-сервиса не теряет пост из будущей ленты: обработка повторяется и завершается терминально без зависания, факт сбоя фиксируется наблюдаемым образом.
- `REQ-07` Хранение оценок и интересов остаётся в рамках PostgreSQL — инфраструктуры MVP ([architecture.md → Job queue / Scheduling](../../domain/architecture.md#job-queue--scheduling)).
- `REQ-08` Операции скоринга и выдачи ленты покрыты автотестами согласно [testing-policy](../../engineering/testing-policy.md).

### Non-Scope

- `NS-01` Пользовательский интерфейс (React UI) — ранжированную ленту визуализирует FT-011; здесь только её программная выдача через API/feediumctl.
- `NS-02` Telegram-бот OpenClaw (FT-012).
- `NS-03` Обучение/файнтюнинг моделей и персонализация по обратной связи (лайки/дизлайки, обучение на поведении) — post-MVP-гипотезы (`RISK-01` mitigation, [PRD-001 → Risks](../../prd/PRD-001-mvp.md#risks-and-open-questions)).
- `NS-04` Тематическая классификация и дедупликация постов (`OQ-03`/`OQ-04` PRD-001).
- `NS-05` Массовый ретроактивный пере-скоринг всей исторической ленты при изменении интересов: оцениваются посты по мере появления их Summary, а не весь архив.
- `NS-06` Мультипользовательские профили интересов и пользовательская аутентификация (`PCON-01`).
- `NS-07` Выбор метода оценки, моделей, способа хранения и поиска векторов, порогов отсечения, формата оценки и механизма постановки оценки в очередь — фиксируется на Design-фазе (см. `## Open Questions`), а не в этом документе.
- `NS-08` Изменение поведения пайплайна FT-005 / FT-007: outbox, lease/retry на уровне summary-события, per-source `next_summary_at`, lifecycle Summary Worker — не трогаются. FT-010 потребляет Summary как вход и добавляет скоринг downstream (`BR-04`).
- `NS-09` Подъём или переопределение project-level метрик `MET-03` / `MET-04` PRD-001 как собственных KPI FT-010 и фиксация конкретного numeric-порога качества/задержки скоринга как success threshold.

### Constraints / Assumptions

- `ASM-01` У поста уже существует `Summary` (FT-005, [`internal/ent/schema/summary.go`](../../../internal/ent/schema/summary.go), [FT-005 spec](../FT-005-ai-summarization/spec.md)) — он является входом для оценки релевантности. FT-010 не реализует суммаризацию заново.
- `ASM-02` Доступен outbox + pull-модель обработки событий с атомарным захватом, lease, retry с backoff и санацией зависших записей (FT-007, [FT-007 feature](../FT-007-scalable-event-processing/feature.md)) — это референс-паттерн для автоматического скоринга после Summary. Shared state — только через PostgreSQL, отдельная очередь (Redis/NATS) не вводится (`ASM` совпадает с [architecture.md → Job queue / Scheduling](../../domain/architecture.md#job-queue--scheduling)).
- `ASM-03` Управление интересами как новой управляемой сущностью повторяет CRUD-модель и поверхность API/feediumctl источников (FT-003, [`api/feedium/source.proto:105-137`](../../../api/feedium/source.proto), [FT-003 spec](../FT-003-source-management/spec.md)) и не вводит пользовательскую аутентификацию.
- `ASM-04` Пользователь системы один; набор интересов глобален для инстанса, без понятия владельца и без мультипрофилей ([problem.md → Product Context](../../domain/problem.md#product-context), `PCON-01`).
- `CON-01` Скоринг опирается на внешний платный AI-сервис с известными рисками: стоимость при потоке до 10 000 постов в день (`RISK-02`) и доступность/латентность провайдера (`RISK-05`). Design обязан учесть экономику и деградацию при сбоях ([PRD-001 → Risks](../../prd/PRD-001-mvp.md#risks-and-open-questions), `PCON-03`).
- `CON-02` Скоринг асинхронен относительно появления поста в хранилище: оценка считается downstream события Summary и не блокирует request-path; задержка появления контента (`MET-03` PRD-001) не должна расти из-за скоринга (`RISK-05` mitigation — асинхронный скоринг, очередь).
- `CON-03` Гарантия «ровно одна актуальная оценка на пост» — инвариант, обеспечиваемый на уровне БД (уникальность актуальной оценки по посту), аналогично инварианту уникальности активного события FT-005/FT-007. Любая реализация скоринга не должна ослаблять его.
- `CON-04` Применимы `PCON-*` из [problem.md → Constraints](../../domain/problem.md#constraints): `PCON-01` single-user; `PCON-03` стоимость и латентность LLM ограничивают глубину и частоту AI-процессинга; `PCON-05` обрабатывается текстовый контент. Стек server-side (Go 1.25+, kratos-layout, PostgreSQL 18.3); desktop/Windows-only решения недопустимы.
- `CON-05` Добавление скоринга не меняет поведение существующих типов источников и режимов суммаризации (`BR-04`); схема `posts` FT-004 структурно не меняется — оценка хранится как отдельная связанная сущность (`CTR-06`).

## How

### Solution

Ввести две новые управляемые сущности в рамках PostgreSQL — `Interest` (глобальный для инстанса набор интересов с CRUD-поверхностью, повторяющей FT-003) и `Score` (актуальная оценка релевантности поста, ровно одна на пост) — и автоматический скоринг как downstream-этап после завершения Summary: воркер в `task/` по событию готовности Summary атомарно захватывает пост (pull-модель, lease, retry — референс FT-007), вычисляет релевантность относительно текущего набора интересов через внешний AI-клиент, определённый интерфейсом в `biz/`, и сохраняет ровно одну актуальную оценку (upsert по посту). Отранжированная лента — новый read-контракт (proto + service + feediumctl), отдающий посты по убыванию оценки с фильтрацией по времени и порогу; явно нерелевантный контент получает низшую оценку и оказывается в хвосте, оставаясь доступным. Главный trade-off: переиспользуется уже построенный outbox/pull-каркас FT-007 поверх PostgreSQL (никаких внешних очередей и vector-store вне MVP-инфраструктуры — проще и дешевле в эксплуатации, но конкретный метод оценки и способ хранения/поиска векторов ограничены тем, что укладывается в PostgreSQL и экономику провайдера).

Конкретный метод оценки (эмбеддинги, LLM-судья или их сочетание), выбор моделей, способ хранения и поиска векторов, пороги отсечения, формат оценки и механизм постановки оценки в очередь — решения Design-фазы, фиксируются в sibling [`implementation-plan.md`](implementation-plan.md) и закрывают `OQ-01` PRD-001. Бизнес-контракт FT-010 от выбора этих механизмов не зависит.

### Flow

1. **Вход.** Пост с завершённым `Summary` (FT-005, `ASM-01`) и текущий глобальный набор `Interest` (`REQ-01`).
2. **Обработка.** По готовности Summary scoring-воркер `task/` автоматически и без ручного вызова захватывает пост (атомарный захват, lease — референс FT-007, `ASM-02`), вычисляет релевантность поста относительно текущего набора интересов через внешний AI-клиент (`biz/` порт) и сохраняет ровно одну актуальную оценку upsert-ом по посту (`REQ-02`, `REQ-05`, `CON-03`). Явно нерелевантный пост получает низшую оценку (`REQ-03`). Transient-сбой AI-сервиса → событие скоринга возвращается в очередь с экспоненциальной задержкой до терминального завершения; пост остаётся в хранилище и пригоден для будущей ленты, факт сбоя наблюдаем (`REQ-06`).
3. **Выход.** У поста — одна актуальная оценка. Отранжированная лента (API + feediumctl) возвращает посты по убыванию оценки с фильтрацией по времени и порогу (`REQ-04`); нерелевантный контент — в хвосте, доступен по get (`REQ-03`). Смена набора интересов наблюдаемо меняет оценку постов, оцениваемых после изменения, без ретроактивного пере-скоринга истории (`REQ-01`, `NS-05`).

| `CTR-06` | Новые сущности `interest`/`score` добавляются как отдельные таблицы PostgreSQL; схема `posts` (FT-004) структурно не меняется, поведение существующих типов источников и режимов суммаризации сохраняется. | schema | `BR-04`; UUID v7 PK, TIMESTAMPTZ, FK обязательны ([database.md](../../engineering/database.md)) |

### Failure Modes

- `FM-01` **Внешний AI-сервис временно недоступен (таймаут, 5xx, обрыв соединения)** (`RISK-05`). Событие скоринга возвращается в очередь с экспоненциальной задержкой; после исчерпания попыток — терминальный `failed`. Пост остаётся в хранилище и пригоден для будущей ленты, факт сбоя зафиксирован наблюдаемым образом (`REQ-06`, `CTR-07`).
- `FM-02` **AI-сервис вернул permanent-ошибку (валидационная, 4xx).** Событие скоринга переводится в терминальный `failed` без дополнительных попыток; пост не выпадает из хранилища и остаётся доступным; сбой наблюдаем. Размещение ещё не оценённого поста в ленте определяется Design (`OQ-06`), но пост никогда не теряется.
- `FM-03` **Несколько воркеров/процессов одновременно претендуют на скоринг одного поста.** Атомарный захват + инвариант уникальности актуальной оценки гарантируют ровно одну актуальную оценку без дубликатов (`REQ-05`, `CON-03`).
- `FM-04` **Повторная оценка поста (re-trigger, восстановление после crash, смена интересов).** Upsert обновляет актуальную оценку на месте, не создаёт второй актуальной записи (`CTR-02`).
- `FM-05` **Поток до 10 000 постов в день нагружает платный AI-сервис** (`RISK-02`). Скоринг асинхронен и не блокирует появление контента (`CON-02`); экономия (batch/кэширование эмбеддингов) — обязательное требование к Design (`CON-01`); деградация при превышении наблюдаема.
- `FM-06` **Явно нерелевантный контент.** Получает низшую оценку и оказывается в хвосте ленты, не удаляется и доступен по get (`REQ-03`).

### ADR Dependencies

Новых ADR FT-010 превентивно не вводит: outbox + pull-модель обработки событий поверх PostgreSQL уже зафиксированы FT-007 и [architecture.md](../../domain/architecture.md) как принятый MVP-паттерн, а CRUD-сущность с API/feediumctl-поверхностью — FT-003. Если на Design-фазе выбор, значимый для будущих фич, окажется архитектурным решением, фиксируемым как инвариант (например, метод оценки, размерность/модель эмбеддингов, способ хранения и поиска векторов в PostgreSQL, формат и диапазон оценки), он оформляется отдельным ADR в `memory-bank/adr/` в момент появления и блокирует соответствующие решения до перевода в `accepted` (`proposed` не считается finalized design).

На Design-фазе такой выбор возник: метод оценки, способ хранения/поиска векторов в PostgreSQL и формат оценки зафиксированы в [`ADR-001`](../../adr/ADR-001-scoring-method-and-vector-storage.md) (`decision_status: accepted`, 2026-06-02). `spec.md` `DEC-01..04` derive из него.

## Verify

`Verify` задаёт canonical test case inventory FT-010: positive scenarios через `SC-*`, error/edge/nfr coverage через `SC-*` соответствующего kind, executable checks через `CHK-*` и evidence через `EVID-*`. Сценарии end-to-end: от входного события (готовность Summary / запрос ленты / операция над интересом) до наблюдаемого результата через все затронутые слои. Внешний AI-сервис подменяется детерминированным test double согласно [testing-policy → Когда Manual-Only Допустим](../../engineering/testing-policy.md#когда-manual-only-допустим): mock scoring-клиента с управляемой релевантностью и управляемыми сбоями.

### Exit Criteria

- `EC-01` Интерес можно задать, увидеть в списке, изменить и удалить через API и feediumctl.
- `EC-02` Просуммированный пост получает оценку релевантности без ручного вызова скоринга.
- `EC-03` Отранжированная лента через API и feediumctl возвращает посты по убыванию оценки с корректной фильтрацией по времени и по порогу.
- `EC-04` Явно нерелевантный пост получает низшую оценку, оказывается в хвосте ленты и остаётся доступным по get.
- `EC-05` У каждого просуммированного поста ровно одна актуальная оценка; параллельная обработка несколькими воркерами/процессами не порождает дубликатов оценок.
- `EC-06` При недоступном AI-сервисе обработка поста повторяется и завершается терминально без зависания; пост не выпадает из будущей ленты; факт сбоя зафиксирован наблюдаемым образом.
- `EC-07` Изменение набора интересов наблюдаемо влияет на оценку постов, оцениваемых после изменения; ретроактивный массовый пере-скоринг истории не выполняется.
- `EC-08` Операции скоринга и выдачи ленты покрыты автотестами; `make build && make test && make lint` зелёные локально и в CI.

### Acceptance Scenarios

- `SC-01` **CRUD интересов (happy).** Дано: запущенный feedium-сервер. Когда: пользователь через API/feediumctl создаёт интерес, запрашивает список, изменяет и удаляет интерес. Тогда: список отражает каждую операцию (создание видно, изменение применено, после удаления отсутствует), все операции завершаются успешно. kind: happy.
- `SC-02` **Авто-скоринг просуммированного поста (happy).** Дано: пост с завершённым Summary и непустой набор интересов; mock scoring-клиента отдаёт релевантность. Когда: scoring-воркер отрабатывает событие готовности Summary. Тогда: у поста появляется ровно одна актуальная оценка без ручного вызова scoring-API. kind: happy.
- `SC-03` **Отранжированная лента (happy).** Дано: набор постов с разными оценками. Когда: запрашивается лента через API/feediumctl с фильтром по диапазону времени и по порогу оценки. Тогда: возвращены посты по убыванию оценки, посты вне диапазона времени и ниже порога отфильтрованы; в машиночитаемом формате вывод парсится без пост-обработки. kind: happy.
- `SC-04` **Нерелевантный контент в хвосте (edge).** Дано: пост, явно не отвечающий интересам (mock-клиент возвращает низшую релевантность). Когда: пост оценён и запрошена лента. Тогда: пост получает низшую оценку, оказывается в хвосте отранжированной выдачи и остаётся доступным по get (не удалён). kind: edge.
- `SC-05` **Идемпотентность повторной оценки (edge).** Дано: уже оценённый пост. Когда: скоринг поста запускается повторно. Тогда: актуальная оценка обновляется на месте, у поста остаётся ровно одна актуальная оценка, дубликаты не созданы. kind: edge.
- `SC-06` **Конкурентный скоринг без дубликатов (nfr).** Дано: одна БД, M процессов × N воркеров, общий набор просуммированных постов; mock scoring-клиента. Когда: воркеры работают одновременно. Тогда: у каждого поста ровно одна актуальная оценка, 0 дубликатов, каждый пост оценён без двойной обработки. kind: nfr.
- `SC-07` **Устойчивость к сбою AI-сервиса (error).** Дано: mock scoring-клиента возвращает transient-ошибку заданное число раз, затем успех (и отдельный прогон — permanent-ошибку). Когда: scoring-воркер обрабатывает событие. Тогда: при transient — событие переоценивается с экспоненциальной задержкой и завершается успешно; при исчерпании попыток/permanent — терминальный `failed`; в обоих случаях пост остаётся в хранилище и пригоден для будущей ленты, сбой зафиксирован наблюдаемым образом, зависания нет. kind: error.
- `SC-08` **Наблюдаемый эффект смены интересов (edge).** Дано: пост, оценённый при наборе интересов A. Когда: набор интересов изменён на B и оценивается новый просуммированный пост. Тогда: оценка нового поста отражает интересы B; ранее оценённые исторические посты не пере-скорятся массово (`NS-05`). kind: edge.
- `SC-09` **Тесты и сборка зелёные (nfr).** Дано: реализованные скоринг и выдача ленты. Когда: запускается `make build && make test && make lint`. Тогда: сборка, тесты и линт зелёные; операции скоринга и ленты покрыты автотестами. kind: nfr.

## Open Questions

Вопросы, ответы на которые относятся к Design-фазе (`implementation-plan.md`); фиксируются здесь как явный input и не закрываются по умолчанию при имплементации. Ни один из них не блокирует Design Ready — бизнес-контракт FT-010 от их разрешения не зависит (`NS-07`). `OQ-01` закрывает одноимённый open question PRD-001.

- `OQ-01` **Метод оценки релевантности.** Эмбеддинги, LLM-судья или их сочетание; выбор моделей. Критерии: качество скоринга (`RISK-01`), стоимость при потоке до 10 000 постов/день (`RISK-02`, `CON-01`), латентность относительно `MET-03` (`RISK-05`, `CON-02`). Закрывает `OQ-01` [PRD-001](../../prd/PRD-001-mvp.md#risks-and-open-questions).
- `OQ-02` **Способ хранения и поиска векторов в рамках PostgreSQL.** pgvector, предвычисленные значения или вычисление на запрос — в границах MVP-инфраструктуры (`REQ-07`, `CON-04`).
- `OQ-03` **Формат и диапазон оценки.** Что конкретно есть «низшая оценка» (`REQ-03`); семантика порога фильтрации ленты (`REQ-04`).
- `OQ-04` **Механизм триггера и очереди скоринга.** Переиспользование outbox + pull (отдельное событие скоринга по аналогии с `SummaryEvent` FT-007) либо иной механизм; ключ идемпотентности (`CTR-02`, `CTR-03`).
- `OQ-05` **Представление интересов и распространение их изменений на скоринг.** Свободные темы, веса, эмбеддинги; как изменение набора интересов влияет на последующую оценку без ретроактивного пере-скоринга (`CTR-05`, `NS-05`).
- `OQ-06` **Размещение ещё не оценённых постов в ленте.** Поведение для постов с отложенным/проваленным скорингом (`FM-01`, `FM-02`): порядок относительно оценённых постов при гарантии, что пост никогда не теряется (`REQ-06`).
- `OQ-07` **Дефолтные параметры скоринга.** Конкурентность, lease, retry/backoff, дефолтный порог; переиспользование конвенций FT-007 (`ASM-02`, `CON-01`).
