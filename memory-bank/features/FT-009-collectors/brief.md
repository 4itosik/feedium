# FT-009: Content Collectors

## Problem

Сегодня единственный путь, которым пост попадает в Feedium, — ручной вызов API создания поста. Ни один источник не опрашивается автоматически: добавленный источник (RSS-фид, Telegram-канал, веб-сайт) хранится в системе, но никакого контента сам по себе не приносит.

Последствия бездействия:

- Полностью блокируется G-01 PRD-001 («открыл Feedium — получил ленту за день»): без автоматического сбора лента пуста, пока пользователь вручную не перенесёт каждый пост.
- Текущее состояние строго хуже исходной боли: вместо обхода 10+ источников пользователь должен вручную скопировать каждый пост в API — это не заменяет ручной обход, а добавляет работы.
- Простаивает уже построенный downstream-конвейер (FT-005 суммаризация, FT-007 обработка событий): ему нечего обрабатывать, пока посты не поступают.
- North Star PRD-001 недостижим: пользователь не может перестать ходить в источники руками, потому что система не ходит в них за него.

## Task

Обеспечить автоматический сбор текстовых постов из настроенных источников и их сохранение во внутреннее хранилище без ручного вмешательства, для всех четырёх типов источников, уже известных системе (BR-01): Telegram-каналы, Telegram-группы, RSS-фиды, веб-сайты.

1. Для каждого настроенного источника система периодически забирает новый контент и сохраняет его как посты — без вызова API пользователем.
2. Сбор не нарушает дифференцированный режим обработки (BR-01): self-contained источники (канал, RSS, веб) и cumulative источники (Telegram-группа) после сбора попадают в свой режим суммаризации без изменения его поведения (BR-04).
3. Повторный сбор того же материала не создаёт дубликатов постов.
4. Сбой сбора одного источника (недоступный фид, изменившаяся страница, ошибка соединения) не останавливает сбор остальных источников и наблюдаем.

Конкретные библиотеки и клиенты, механизм планирования опроса, способ хранения учётных данных и сессии Telegram, стратегия извлечения контента из HTML, частота опроса по умолчанию — задача Design-фазы.

## Context

- Разрабатывается MVP Feedium; FT-001..FT-007 обеспечивают каркас, хранилище, управление источниками и постами, суммаризацию и масштабируемую обработку событий. Сбор — недостающее звено, которое наполняет всю цепочку.
- Источник уже хранит свой тип и режим обработки (FT-003); пост уже хранит источник, дату публикации, автора и внешний идентификатор материала (FT-004). Сбор должен наполнять эти поля, а не вводить новые сущности.
- Поводом служит то, что без сбора ни одна из последующих фич (скоринг, лента, дайджесты OpenClaw) не имеет входных данных — FT-009 разблокирует продуктовую ценность MVP.
- Сбор затрагивает внешние системы с известными рисками PRD-001: блокировка Telegram-userbot (RISK-03) и хрупкость веб-скрапинга при смене вёрстки (RISK-04). Design обязан учесть деградацию и изоляцию отказов между источниками.
- На этапе MVP собираются только текстовые посты (BR-05); к каждому посту сохраняются источник и метаданные (BR-06).
- Объём потока — до 10 000 постов в день (RISK-02 PRD-001); Design обязан учесть экономику и нагрузку при таком потоке.

## Users

- **Пользователь Feedium** — перестаёт обходить источники вручную: контент приходит в систему сам и далее суммаризируется без его участия.

## Scope

### In Scope

- Автоматический периодический сбор постов из RSS-фидов.
- Автоматический сбор постов из Telegram-каналов (self-contained) и Telegram-групп (cumulative).
- Автоматический сбор постов из веб-сайтов.
- Сохранение каждого собранного поста с источником, датой публикации, автором (если доступен), внешним идентификатором материала и метаданными (BR-06).
- Идемпотентность сбора: повторный сбор не создаёт дубликатов постов.
- Изоляция отказов: сбой одного источника не прерывает сбор остальных и фиксируется наблюдаемым образом.
- Частота опроса источников задаётся конфигурацией системы.
- Автотесты операций сбора согласно testing-policy проекта.

### Out Of Scope

- AI-скоринг и ранжирование собранных постов (следующая фича).
- Пользовательский интерфейс (React UI) и Telegram-бот OpenClaw.
- Сбор нетекстового контента — изображений, видео, файлов (BR-05).
- Массовый импорт полного исторического архива источника: собирается контент, поступающий с момента подключения источника, а не вся история.
- Выбор библиотек, клиентов, механизма планирования, способа хранения сессии/секретов, стратегии извлечения из HTML — задача Design-фазы.
- Аутентификация и авторизация пользователей Feedium.
- Управление источниками (CRUD) — закрыто FT-003.

## Acceptance Criteria

- Настроенный источник типа RSS, Telegram-канал или веб-сайт начинает порождать посты в хранилище без ручного вызова API.
- Настроенная Telegram-группа порождает собранные сообщения, которые попадают в cumulative-режим обработки.
- Self-contained источник после сбора поста запускает суммаризацию этого поста; cumulative источник накапливает посты для периодической суммаризации — поведение режимов из FT-005 не меняется (BR-04).
- Повторный сбор источника без нового контента не создаёт дубликатов постов.
- Каждый собранный пост содержит источник, дату публикации, внешний идентификатор материала и метаданные; автор сохраняется, если доступен в источнике.
- Сбор каждого источника выполняется с периодичностью, заданной в конфигурации системы.
- Сбой сбора одного источника не останавливает сбор остальных источников и фиксируется наблюдаемым образом (запись об ошибке).
- Собираются только текстовые посты (BR-05).
- Операции сбора покрыты автотестами согласно testing-policy проекта.
