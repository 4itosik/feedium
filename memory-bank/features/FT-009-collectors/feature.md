# FT-009-collectors: Content Collectors

## What

Выбран `large.md`. Rationale: фича пронизывает несколько поверхностей (`task/` коллекторы, `biz/` usecase сбора, `data/` внешние клиенты, конфиг), вводит новый config/env-контракт (частота опроса, хранение учётных данных и сессии Telegram), требует явных `ASM-*` / `CON-*` / `CTR-*` / `FM-*` (внешние системы с известными рисками RISK-03/RISK-04), нескольких acceptance scenarios (по одному на каждый из 4 типов источников плюс idempotency, isolation, config, text-only) и нескольких `CHK-*` / `EVID-*`. Любое из этих условий уже исключает `short.md` ([feature-flow.md §Выбор шаблона](../../flows/feature-flow.md#выбор-шаблона-featuremd)).

### Problem

Сегодня единственный путь, которым пост попадает в Feedium, — ручной вызов API создания поста (FT-004). Источник, добавленный через FT-003, хранит свой тип и режим обработки, но сам по себе не приносит контента: ни один коллектор `task/`, описанный в [architecture.md → Module Boundaries](../../domain/architecture.md#module-boundaries) и [glossary.md → Коллектор](../../domain/glossary.md#коллектор), пока не реализован.

Это feature-specific delta относительно PRD-001: общая постановка ингестии зафиксирована в [problem.md → Core Workflows `WF-01`](../../domain/problem.md#core-workflows); FT-009 закрывает конкретный недостающий шаг — автоматическое наполнение хранилища.

Последствия бездействия:

- Блокируется `G-01` PRD-001 («открыл Feedium — получил ленту за день», [PRD-001 → Goals](../../prd/PRD-001-mvp.md#goals)): без автоматического сбора лента пуста, пока пользователь вручную не перенесёт каждый пост.
- Текущее состояние строго хуже исходной боли: вместо обхода 10+ источников пользователь должен вручную скопировать каждый пост в API — это добавляет работы, а не заменяет ручной обход (`MET-02`, [problem.md → Outcomes](../../domain/problem.md#outcomes)).
- Простаивает уже построенный downstream-конвейер: суммаризация (FT-005) и масштабируемая обработка событий (FT-007) не имеют входных данных.
- North Star PRD-001 недостижим: система не ходит в источники за пользователем.

### Outcome

| `MET-03` | Изоляция отказа одного источника | N/A (сбора нет) | Сбой одного источника не уменьшает число собранных постов из исправных источников; ошибка наблюдаема | Интеграционный тест: один источник возвращает ошибку, остальные собирают посты; зафиксирована запись об ошибке |

`MET-03` PRD-001 (задержка публикация → появление в ленте < 5 минут, [problem.md → Outcomes](../../domain/problem.md#outcomes)) зависит от частоты опроса и от downstream-суммаризации; FT-009 владеет только сбором и не переопределяет этот project-level threshold (см. `NS-09`).

### Scope

- `REQ-01` Система периодически и автоматически собирает новые посты из настроенных RSS-фидов и сохраняет их без вызова create-API пользователем.
- `REQ-02` Система автоматически собирает посты из настроенных Telegram-каналов (self-contained режим).
- `REQ-03` Система автоматически собирает сообщения из настроенных Telegram-групп (cumulative режим).
- `REQ-04` Система автоматически собирает посты из настроенных веб-сайтов.
- `REQ-05` Каждый собранный пост сохраняется с источником, датой публикации, внешним идентификатором материала и метаданными; автор сохраняется, если доступен в источнике (BR-06, поля FT-004).
- `REQ-06` Повторный сбор того же материала не создаёт дубликатов постов (идемпотентность сбора поверх гарантии уникальности FT-004).
- `REQ-07` Сбой сбора одного источника (недоступный фид, изменившаяся страница, ошибка соединения, rate-limit) не останавливает сбор остальных источников и фиксируется наблюдаемым образом (запись об ошибке).
- `REQ-08` Частота опроса источников задаётся конфигурацией системы.
- `REQ-09` После сбора self-contained источник (канал, RSS, веб) запускает суммаризацию поста, cumulative источник (Telegram-группа) накапливает посты для периодической суммаризации; поведение режимов FT-005 не меняется (BR-04).
- `REQ-10` Собираются только текстовые посты; нетекстовый материал не порождает Post в MVP (BR-05).
- `REQ-11` Операции сбора покрыты автотестами согласно [testing-policy](../../engineering/testing-policy.md).

### Non-Scope

- `NS-01` AI-скоринг и ранжирование собранных постов — следующая фича.
- `NS-02` Пользовательский интерфейс (React UI) и Telegram-бот OpenClaw.
- `NS-03` Сбор нетекстового контента — изображений, видео, файлов (BR-05).
- `NS-04` Массовый импорт полного исторического архива источника: собирается контент, поступающий с момента подключения источника, а не вся история.
- `NS-05` Выбор библиотек, клиентов, механизма планирования опроса, способа хранения сессии/секретов Telegram и стратегии извлечения из HTML — фиксируется на Design-фазе (см. `## Open Questions`), а не в этом документе.
- `NS-06` Аутентификация и авторизация пользователей Feedium.
- `NS-07` Управление источниками (CRUD) — закрыто FT-003; FT-009 только читает уже сохранённые источники.
- `NS-08` Изменение пайплайна FT-005 / FT-007: outbox, lease/retry на уровне события, per-source `next_summary_at`, расписание cron, lifecycle Summary Worker — не трогаются. FT-009 только поставляет посты на вход этого пайплайна.
- `NS-09` Подъём или переопределение project-level метрики `MET-03` PRD-001 (latency публикация → лента) и выбор дефолтной частоты опроса как KPI — FT-009 делает частоту конфигурируемой (`REQ-08`), но не фиксирует конкретное numeric-значение как success threshold.

### Constraints / Assumptions

- `ASM-01` Источник уже хранит свой тип (`telegram_channel`, `telegram_group`, `rss`, `html`) и режим обработки (self-contained / cumulative) — FT-003 ([FT-003 spec](../FT-003-source-management/spec.md), BR-01).
- `ASM-02` Пост уже хранит источник, дату публикации, автора, внешний идентификатор материала и метаданные, и гарантирует отсутствие дубликатов по материалу источника — FT-004 ([FT-004 spec](../FT-004-posts-management/spec.md)). FT-009 наполняет эти поля, а не вводит новые сущности.
- `ASM-03` Сохранение поста атомарно создаёт событие суммаризации (outbox FT-005); cumulative-материал планируется per-source (FT-007). FT-009 опирается на этот механизм, не реализует его заново ([FT-005 spec](../FT-005-ai-summarization/spec.md), [FT-007 feature](../FT-007-scalable-event-processing/feature.md)).
- `ASM-04` В MVP действует polling-based scheduling; shared state — только через PostgreSQL, отдельная очередь (Redis/NATS) не вводится ([architecture.md → Job queue / Scheduling](../../domain/architecture.md#job-queue--scheduling)).
- `CON-01` Коллекторы живут в `task/` и реализуют kratos `transport.Server`; lifecycle (`Start()/Stop()`) управляет фреймворк. `task/` вызывает `biz/` usecases и не обращается к `data/` напрямую ([architecture.md → Module Boundaries](../../domain/architecture.md#module-boundaries)).
- `CON-02` Обработка ошибок и ретраи — ответственность `task/`; leaf-функции `biz/` / `data/` не логируют. Retry-policy: Telegram — rate-limit aware; web scraping — single retry, при повторной ошибке skip source с логированием ([architecture.md → Failure Handling](../../domain/architecture.md#failure-handling-and-error-tracking)).
- `CON-03` Целевой поток — до 10 000 постов в день (RISK-02 PRD-001); Design обязан учесть нагрузку и экономику downstream-обработки при таком потоке.
- `CON-04` Применимы PCON из [problem.md → Constraints](../../domain/problem.md#constraints): `PCON-01` single-user; `PCON-02` Telegram userbot несёт риск rate-limit/бана, нужен контроль частоты и изоляция аккаунта (RISK-03); `PCON-04` веб-скрапинг хрупкий к смене вёрстки, при наличии RSS предпочтителен RSS (RISK-04); `PCON-05` обрабатывается текстовый контент. Стек server-side (Go + kratos + PostgreSQL); desktop/Windows-only решения недопустимы.
- `CON-05` Добавление коллекторов не меняет поведение существующих типов источников и режимов суммаризации (BR-04).

## How

### Solution

Для каждого типа источника ввести коллектор в `task/`, реализующий kratos `transport.Server` и работающий в polling-цикле с интервалом из конфига: коллектор забирает с внешней системы материал, поступивший с момента предыдущего цикла, отфильтровывает нетекстовый (`REQ-10`), нормализует его в модель Post и передаёт через `biz/` usecase сбора, который сохраняет пост существующим путём FT-004 (дедупликация по внешнему идентификатору материала) и тем самым атомарно инициирует обработку через outbox FT-005 / per-source расписание FT-007. Главный trade-off: 4 типа источников обслуживаются отдельными коллекторами с общим biz-контрактом сохранения, а не единым «универсальным» сборщиком — это даёт изоляцию отказов по источнику (`REQ-07`) и независимую rate-limit/retry-политику на тип (`CON-02`) ценой повторяющегося lifecycle-каркаса в `task/`.

Конкретные библиотеки и клиенты (Telegram userbot: gotd/td vs go-tdlib; RSS-парсер; HTTP/HTML-извлечение), механизм планирования опроса, способ хранения учётных данных и сессии Telegram, стратегия извлечения контента из HTML и дефолтная частота опроса — решения Design-фазы, фиксируются в sibling [`implementation-plan.md`](implementation-plan.md). Бизнес-контракт FT-009 не зависит от выбора этих механизмов.

> **Design-delta (DEC-08, реализовано 2026-05-26):** Telegram (`REQ-02`/`REQ-03`) собирается **push-моделью** на `gotd/td` (`updates.Manager`), а не polling — сообщения приходят в реальном времени и прогоняются через тот же biz-путь сбора. Поэтому для Telegram `REQ-08` (частота опроса) **не применяется**, а порт `biz.Fetcher` не используется (вместо него — порт `biz.TelegramSession` + `CollectUsecase.CollectItems`). RSS (`REQ-01`) и web (`REQ-04`) остаются на polling без изменений. Долговечность: in-memory updates-state, без backfill (схема БД не меняется). Полное обоснование и архитектура — [`2026-05-26-telegram-push-design.md`](2026-05-26-telegram-push-design.md).

| Конфигурация коллекторов (частота опроса; расположение учётных данных/сессии Telegram) | config | Частота опроса задаётся конфигом (`REQ-08`); хранение секретов/сессии — новый config/env-контракт, детали — Design (`NS-05`) |

Детали (конкретные файлы, имена символов, сигнатуры, sequence diagrams) — в sibling [`implementation-plan.md`](implementation-plan.md).

### Flow

1. **Вход.** Настроенный источник (FT-003) с типом и режимом обработки. Коллектор соответствующего типа в `task/` по расписанию из конфига (`REQ-08`) опрашивает внешнюю систему и получает материал, поступивший с момента предыдущего цикла (`NS-04`).
2. **Обработка.** Коллектор отфильтровывает нетекстовый материал (`REQ-10`), нормализует каждый текстовый материал в модель Post с полями источника, даты публикации, автора (если доступен), внешнего идентификатора и метаданных (`REQ-05`), и вызывает `biz/` usecase сохранения. `biz/` сохраняет пост существующим путём FT-004: повторный материал отсекается по внешнему идентификатору (`REQ-06`), а успешное сохранение атомарно инициирует обработку через outbox FT-005 / per-source расписание FT-007 (`REQ-09`).
3. **Выход.** Новые посты в PostgreSQL, привязанные к источнику, с метаданными. Self-contained источник → суммаризация запускается сразу; cumulative источник → посты накапливаются для периодической суммаризации (`REQ-09`, BR-04). Ошибка сбора отдельного источника логируется в `task/` и не прерывает сбор остальных источников (`REQ-07`, `CON-02`).

### Contracts

| Contract ID | Input / Output | Producer / Consumer | Notes |
| --- | --- | --- | --- |
| `CTR-01` | Коллектор каждого типа нормализует внешний материал в модель Post (источник, дата публикации, автор?, внешний идентификатор материала, текст, метаданные) и передаёт его `biz/` usecase сохранения. | task → biz | Никаких новых сущностей; поля определены FT-004 (`ASM-02`) |
| `CTR-02` | Сохранение собранного поста использует существующую гарантию уникальности FT-004 по внешнему идентификатору материала: повторный сбор того же материала не создаёт второй Post (skip/no-op). | biz ↔ data | Идемпотентность сбора — производная от инварианта FT-004, не новый механизм |
| `CTR-03` | Сохранение self-contained поста атомарно инициирует суммаризацию (outbox FT-005); cumulative-пост накапливается под per-source расписание FT-007. Форма и контракт FT-005/FT-007 не меняются. | biz → data | Регрессионный покров — существующие тесты FT-005/FT-007 (`NS-08`) |
| `CTR-04` | Частота опроса каждого коллектора берётся из конфигурации системы; коллектор не «зашивает» интервал в код. | conf → task | Конкретные ключи конфига и дефолт — `implementation-plan.md` (`OQ-02`) |
| `CTR-05` | Сбой сбора одного источника изолирован: коллектор источника фиксирует наблюдаемую запись об ошибке в `task/` и продолжает работу/следующий цикл, не влияя на другие источники и другие коллекторы. | task | Web: single retry → skip source; Telegram: rate-limit aware (`CON-02`) |

### Failure Modes

- `FM-01` **Источник недоступен (фид отдаёт ошибку, таймаут, обрыв соединения).** Цикл сбора этого источника фиксирует наблюдаемую ошибку и завершается; остальные источники собираются штатно (`CTR-05`, `REQ-07`).
- `FM-02` **Изменилась вёрстка веб-сайта — извлечение контента не удаётся** (RISK-04, `PCON-04`). Ошибка наблюдаема, источник пропускается (web single-retry-then-skip), остальные источники не затронуты.
- `FM-03` **Telegram rate-limit / угроза бана userbot** (RISK-03, `PCON-02`). Сбор Telegram выполняется rate-limit aware; достижение лимита не валит остальные коллекторы и фиксируется.
- `FM-04` **Повторный или перекрывающийся сбор того же материала.** Уникальность по внешнему идентификатору материала (FT-004) предотвращает дубль Post (`CTR-02`, `REQ-06`).
- `FM-05` **Частичный сбор: часть материалов сохранена, часть упала в том же цикле.** Сохранённые посты остаются и проходят downstream-обработку; ошибка фиксируется; следующий цикл дособирает остаток без дублей (`CTR-02`).
- `FM-06` **В источнике встречается нетекстовый материал (изображение, видео, файл).** Не порождает Post в MVP (BR-05, `REQ-10`); пропускается без ошибки.

### ADR Dependencies

Новых ADR FT-009 не вводит: коллекторы `task/` как `transport.Server` и polling-модель уже зафиксированы в [architecture.md](../../domain/architecture.md) и [glossary.md](../../domain/glossary.md) как принятый MVP-паттерн. Если на Design-фазе выбор, имеющий значение для будущих фич, окажется архитектурным решением (например, фиксация конкретной Telegram-библиотеки или способа хранения сессии как инварианта для downstream), он оформляется отдельным ADR в момент появления и блокирует соответствующие решения до перевода в `accepted`. Превентивно ADR не заводится.

## Verify

`Verify` задаёт canonical test case inventory: positive scenarios через `SC-*`, error/edge coverage через `SC-*` соответствующего kind, executable checks через `CHK-*` и evidence через `EVID-*`. Сценарии end-to-end: от цикла сбора до наблюдаемого результата в хранилище и на входе downstream-пайплайна. Внешние системы (живой Telegram, живые сайты) подменяются детерминированными test doubles согласно [testing-policy → Когда Manual-Only Допустим](../../engineering/testing-policy.md#когда-manual-only-допустим): mock Telegram-клиента, `httptest.Server` с фикстурами RSS/HTML.

### Exit Criteria

- `EC-01` Настроенный источник типа RSS, Telegram-канал или веб-сайт начинает порождать посты в хранилище без ручного вызова create-API.
- `EC-02` Настроенная Telegram-группа порождает собранные сообщения, которые попадают в cumulative-режим обработки.
- `EC-03` Self-contained источник после сбора поста инициирует суммаризацию этого поста; cumulative источник накапливает посты для периодической суммаризации; поведение режимов FT-005 не изменено (BR-04).
- `EC-04` Повторный сбор источника без нового контента не создаёт дубликатов постов.
- `EC-05` Каждый собранный пост содержит источник, дату публикации, внешний идентификатор материала и метаданные; автор сохранён, если доступен в источнике.
- `EC-06` Сбор каждого источника выполняется с периодичностью, заданной в конфигурации системы.
- `EC-07` Сбой сбора одного источника не останавливает сбор остальных источников и фиксируется наблюдаемым образом (запись об ошибке).
- `EC-08` Собираются только текстовые посты; нетекстовый материал не порождает Post.
- `EC-09` Операции сбора покрыты автотестами; `make build && make test && make lint` зелёные.

### Acceptance Scenarios

- `SC-01` **RSS сбор (happy).** Дано: настроенный RSS-источник, `httptest.Server` отдаёт фид с N новыми записями. Когда: коллектор отрабатывает цикл сбора. Тогда: в хранилище появляется N постов, привязанных к источнику, без вызова create-API. kind: happy.
- `SC-02` **Telegram-канал → self-contained (happy).** Дано: настроенный Telegram-канал (self-contained), mock-клиент отдаёт новый пост. Когда: коллектор собирает пост. Тогда: пост сохранён и атомарно инициирована суммаризация этого поста (событие FT-005 создано); поведение self-contained режима не изменено. kind: happy.
- `SC-03` **Telegram-группа → cumulative (happy).** Дано: настроенная Telegram-группа (cumulative), mock-клиент отдаёт новые сообщения. Когда: коллектор собирает сообщения. Тогда: сообщения сохранены как посты cumulative-источника и накапливаются под per-source расписание FT-007, без немедленной per-post суммаризации; поведение cumulative режима не изменено. kind: happy.
- `SC-04` **Веб-сайт сбор (happy).** Дано: настроенный веб-источник, `httptest.Server` отдаёт HTML-фикстуру с текстовой статьёй. Когда: коллектор отрабатывает цикл. Тогда: в хранилище появляется пост с извлечённым текстом и метаданными. kind: happy.
- `SC-05` **Идемпотентность повторного сбора (edge).** Дано: источник, по которому посты уже собраны; внешняя система не отдаёт нового материала. Когда: коллектор отрабатывает второй цикл. Тогда: число постов в хранилище не меняется, дубликаты не созданы. kind: edge.
- `SC-06` **Изоляция отказа источника (error).** Дано: два источника, первый возвращает ошибку соединения, второй отдаёт новый материал. Когда: коллекторы отрабатывают цикл. Тогда: посты второго источника сохранены, по первому зафиксирована наблюдаемая запись об ошибке, сбор не остановлен. kind: error.
- `SC-07` **Сломавшийся веб-парсинг (error).** Дано: веб-источник, чья страница изменила вёрстку так, что извлечение контента не удаётся. Когда: коллектор отрабатывает цикл (single retry → skip). Тогда: источник пропущен с наблюдаемой ошибкой, дубликатов и «полупустых» постов не создано, остальные источники собраны. kind: error.
- `SC-08` **Частота опроса из конфига (nfr).** Дано: конфигурация задаёт интервал опроса. Когда: коллектор работает в течение времени, кратного интервалу. Тогда: число циклов сбора соответствует заданному интервалу, а не «зашитому» значению. kind: nfr.
- `SC-09` **Только текст (edge).** Дано: источник, чей материал содержит нетекстовый элемент (изображение/видео/файл) без текстового тела. Когда: коллектор отрабатывает цикл. Тогда: нетекстовый материал не порождает Post; текстовые материалы того же цикла сохранены. kind: edge.
- `SC-10` **Полнота полей поста (happy).** Дано: источник, чей материал содержит дату публикации, автора, внешний идентификатор и метаданные. Когда: коллектор собирает материал. Тогда: сохранённый пост содержит источник, дату публикации, внешний идентификатор и метаданные; автор сохранён, так как доступен. kind: happy.

## Open Questions

Вопросы, ответы на которые относятся к Design-фазе (`implementation-plan.md`); фиксируются здесь как явный input и не закрываются по умолчанию при имплементации. Ни один из них не блокирует Design Ready — бизнес-контракт FT-009 от их разрешения не зависит (`NS-05`).

- `OQ-01` **Telegram-клиент.** gotd/td vs go-tdlib (см. [glossary.md → Telegram Userbot](../../domain/glossary.md#telegram-userbot)); критерии: rate-limit контроль (`PCON-02`, RISK-03), способ хранения сессии, поддержка каналов и групп.
- `OQ-02` **Механизм и ключи конфигурации частоты опроса.** Единый интервал на все коллекторы или per-type; имена ключей конфига; дефолтное значение (без подъёма как KPI, `NS-09`).
- `OQ-03` **Хранение учётных данных и сессии Telegram.** Где и как (файл, env, секрет-стор) хранится сессия userbot; server-side, без desktop-only решений (`CON-04`).
- `OQ-04` **Стратегия извлечения текста из HTML.** Конкретный подход к парсингу веб-страниц и его хрупкость к смене вёрстки (`PCON-04`, RISK-04, `FM-02`).
- `OQ-05` **Определение «нового материала» с момента подключения источника.** Как коллектор отличает новый материал от уже собранного на старте (cursor / since-метка / только дедупликация по внешнему id), чтобы не тянуть исторический архив (`NS-04`).
- `OQ-06` **Нумерация фичи vs PRD.** ✅ Resolved 2026-05-27: таблица [PRD-001 → Downstream Features](../../prd/PRD-001-mvp.md#downstream-features) перенумерована под фактический каталог `features/` — коллекторы теперь `FT-009` и в PRD; AI-скоринг сдвинут на `FT-010`. Рассинхрон устранён, дублирования идентификатора нет.
