# FT-008: Summarization Prompts Split

## What

### Problem

В FT-005 саммари для всех источников генерируется по единому системному промпту, зашитому в код как Go-константа в data-слое. Этот единственный промпт обслуживает два принципиально разных класса контента, определённых в BR-01:

1. **Self-contained** материал — посты RSS, HTML-статьи, посты Telegram-каналов: один автор, один связный текст, понятный без внешнего контекста.
2. **Cumulative** материал — окно сообщений Telegram-группы: множество участников, реплики-якоря, развитие обсуждения во времени.

Последствия бездействия:

- Любое изменение промпта одновременно затрагивает оба режима: невозможно уточнить инструкции для тредов, не сдвинув поведение для одиночных постов, и наоборот. Любая правка превращается в регрессию-риск для второго класса.
- Текущий промпт писался под одиночный пост: в нём нет ни понятия «участник», ни «реплика», ни «развитие обсуждения». Чтобы добавить эти инструкции в cumulative-режим, сегодня требуется переписать общий промпт целиком — что автоматически меняет поведение для self-contained-режима.
- Промпт-константа внутри функции вызова LLM не существует как самостоятельный артефакт. Маинтейнер промптов, которому не нужно знать архитектуру вызова LLM, вынужден ходить в код, и наоборот — любое ревью промпта тянет за собой ревью data-слоя.

Поводом для разделения служит начало работ над улучшением cumulative-саммари. FT-008 — первый и наименьший шаг этой серии: дальше промпты могут эволюционировать независимо, но эта эволюция (параметризация, runtime-управление, эксперименты, версионирование) намеренно отложена и в скоуп FT-008 не входит.

### Scope

- `REQ-01` В репозитории существуют ровно два системных промпта суммаризации: один для self-contained режима, один для cumulative режима. Оба — самостоятельные артефакты, доступные для рецензии без чтения логики вызова LLM. Их содержимое отличается.
- `REQ-02` При генерации саммари самодостаточного материала LLM-провайдер получает в качестве системного промпта артефакт self-contained режима. При генерации саммари накопительного материала — артефакт cumulative режима.
- `REQ-03` Выбор промпта определяется режимом обработки источника (BR-01, зафиксированным в FT-003) на момент вызова LLM. Никаких иных условий выбора нет.
- `REQ-04` Изменение содержания одного промпта не требует изменений во втором и не влияет на поведение второго режима. Промпты эволюционируют независимо.
- `REQ-05` Поведение FT-005 сохранено: self-contained суммаризация запускается атомарно после сохранения поста; cumulative — по плану FT-007 (per-source `next_summary_at`, ручной запуск через API); повторная обработка идемпотентна.
- `REQ-06` Операции суммаризации в обоих режимах покрыты автотестами согласно testing-policy: тесты подтверждают, что для каждого режима используется соответствующий промпт.

### Non-Scope

- `NS-01` Хранение промптов в БД. Артефакты — часть кодовой базы, версионируются вместе с кодом через git.
- `NS-02` Runtime-управление промптами через API / CLI / UI. Изменение промпта = пересборка и редеплой бинаря.
- `NS-03` Hot-reload промптов без рестарта процесса.
- `NS-04` Версионирование промптов и фиксация «какой промпт был использован» в записи Summary. Сейчас Summary остаётся в том же виде, что и в FT-005.
- `NS-05` A/B-эксперименты, метрики качества саммари, мониторинг регрессии качества.
- `NS-06` Параметризация и шаблонизация промптов переменными источника (название канала, дата окна, тип источника). Откладывается как отдельная фича.
- `NS-07` Изменения пайплайна FT-005 / FT-007: outbox, ретраи, расписание cron, lifecycle Summary Worker, lease/retry-политика — не трогаются.
- `NS-08` Замена или добавление LLM-провайдеров; изменение модели; изменение лимитов `max_input_chars` / `max_window`.
- `NS-09` Любой UI для отображения или редактирования промптов.
- `NS-10` Изменение содержания промптов «по существу» (улучшение качества cumulative-инструкций, переписывание под диалоговую структуру). FT-008 даёт только архитектурное разделение; содержательная эволюция cumulative-промпта — задача следующей итерации поверх FT-008.

### Constraints / Assumptions

- `ASM-01` Режим обработки источника известен бизнес-логике на момент вызова LLM (FT-003, BR-01). Дополнительной классификации не требуется.
- `ASM-02` Раскладка артефактов соответствует границам слоёв biz / data / service, зафиксированным в [architecture.md](../../domain/architecture.md). Промпт — это вход LLM-провайдера, поэтому ответственность за его доставку до провайдера лежит на data-слое; решение о том, какой именно промпт использовать, остаётся в biz-слое.
- `ASM-03` Промпты — статический контент, известный на момент сборки бинаря. Загрузка не требует сети, БД или внешних сервисов.
- `CON-01` Инварианты FT-005 сохраняются: атомарность сохранения поста и инициации суммаризации, идемпотентность повторной обработки, уникальный индекс активного события на post / source.
- `CON-02` Инварианты FT-007 сохраняются: per-source `next_summary_at` для cumulative-источников, безопасный multi-instance запуск, lease-recovery, экспоненциальный retry на уровне события.
- `CON-03` Контракт LLM-провайдера (формат запроса, поля `system` / `user`, лимиты) не меняется. FT-008 меняет только источник значения системного промпта, не его форму.

## How

### Solution

Вынести оба системных промпта суммаризации из тела data-функции в самостоятельные артефакты внутри репозитория и сделать выбор нужного артефакта явной операцией бизнес-логики, опирающейся на режим обработки источника.

Главный trade-off: вместо одной точки изменения появляются две — добавляется индирекция (артефакт ↔ код, который его подгружает), но взамен снимается связность между режимами. На текущей точке развития (две независимые серии правок промптов уже на горизонте) индирекция дешевле, чем сохранение единственного промпта.

Конкретный механизм хранения (отдельный `.txt` / `.md` файл, embed через `go:embed`, отдельная Go-константа в выделенном файле и т.п.), способ выбора промпта в коде (свич по полю режима, отображение через map, инжекция через интерфейс), формат файла, изменения интерфейса LLM-провайдера и стратегия загрузки (build-time / lazy / eager) — решения Design-фазы, фиксируются в sibling [`implementation-plan.md`](implementation-plan.md). Бизнес-контракт FT-008 не зависит от выбора этих механизмов.

### Change Surface

| Surface | Why it changes |
| --- | --- |
| Содержимое промпта суммаризации | Текущая единая константа расщепляется на два значения: self-contained и cumulative. Содержимое self-contained-промпта остаётся семантически эквивалентным сегодняшнему общему промпту (без улучшений по существу — это NS-10). Cumulative-промпт стартует с того же baseline, чтобы FT-008 был изоморфен по поведению, и расходится с self-contained только в следующих итерациях. |
| Раскладка промптов | Из встроенной в data-функцию константы — в самостоятельный артефакт (или артефакты), доступный для рецензии без чтения окружающего кода. |
| LLM-вызов суммаризации (data-слой) | Источник значения системного промпта становится параметром, а не зашитой константой. Форма запроса к провайдеру не меняется. |
| Точка выбора промпта (biz-слой) | Появляется явное правило «по режиму источника — соответствующий промпт». Сегодня такое правило отсутствует, потому что промпт один. |
| Конфигурация | Без изменений. Промпт не становится конфигурируемым (см. NS-02). |
| Схема БД | Без изменений. Summary продолжает храниться без отметки об использованном промпте (см. NS-04). |

Детали (конкретные файлы, имена символов, сигнатуры, sequence diagrams) — в sibling [`implementation-plan.md`](implementation-plan.md).

### Failure Modes

- `FM-01` **Mismatch: self-contained источник получил cumulative промпт (или наоборот).** Контракт CTR-02 нарушен. Должно ловиться автотестом ещё до выкатки; рантайм-валидация не требуется (режим источника детерминирован и не меняется на лету).
- `FM-02` **Один из артефактов пуст или отсутствует на момент сборки/запуска.** Если выбран механизм embed на этапе сборки — ловится компиляцией. Если выбран механизм рантайм-загрузки — обязана быть проверка на старте процесса (а не при первом вызове LLM), чтобы не падать в середине обработки события. Решение и место проверки — в implementation-plan.
- `FM-03` **Случайный copy-paste между артефактами привёл к идентичному содержимому.** Сам по себе не нарушает контракт (промпты могут совпадать), но делает изменение в одном артефакте «бесполезным» с точки зрения цели FT-008. Видимый сигнал — диагностический; жёсткой валидации не требуется.
- `FM-04` **Регрессия инвариантов FT-005 / FT-007.** Атомарность, идемпотентность, lease-recovery, per-source due — не должны измениться. Покрывается существующими тестами FT-005 / FT-007 как regression suite.
- `FM-05` **LLM-провайдер возвращает результат, нерепрезентативный для нового cumulative-промпта.** Поскольку cumulative-промпт в FT-008 остаётся семантически эквивалентным baseline (NS-10), такой риск не материализуется в этой итерации. После содержательной правки cumulative-промпта (вне FT-008) необходимо вернуться к вопросу качества — но это уже out of scope.

### ADR Dependencies

Новых ADR не вводится. FT-008 — локальное архитектурное уточнение, ортогональное LLM-провайдеру, схеме данных и пайплайну. Если в Design-фазе будет принято решение, имеющее значение для будущих фич (например, «промпты в принципе хранятся как .md-файлы, embed через `go:embed`, путь — `internal/.../prompts/`»), оно фиксируется ADR-документом в момент появления, и блокирует соответствующие решения downstream до перевода в `accepted`. Принимать ADR превентивно, до возникновения необходимости — не требуется.

## Primary User Flow

### Поток 1. Self-contained — RSS / HTML / Telegram-канал

1. Коллектор сохраняет новый пост в БД (FT-004).
2. Атомарно с сохранением создаётся событие суммаризации (FT-005).
3. Summary Worker (FT-007) захватывает событие, читает источник и определяет, что режим обработки — **self-contained**.
4. Бизнес-логика выбирает **self-contained промпт** (CTR-02) и передаёт его data-слою.
5. Data-слой вызывает LLM-провайдер, передавая содержимое self-contained промпта в качестве системного (CTR-03, CTR-06).
6. Полученный текст саммари сохраняется как Summary; событие переходит в `completed` (инварианты FT-005 / FT-007 не меняются).

### Поток 2. Cumulative — Telegram-группа по крону

1. Per-source планировщик (FT-007) видит, что у cumulative-источника наступило `next_summary_at`, и захватывает источник.
2. Атомарно создаётся cumulative-событие; `next_summary_at` сдвигается на интервал.
3. Summary Worker захватывает событие, определяет, что режим — **cumulative**.
4. Бизнес-логика выбирает **cumulative промпт** (CTR-02) и передаёт его data-слою.
5. Data-слой вызывает LLM-провайдер, передавая содержимое cumulative промпта в качестве системного (CTR-03, CTR-06).
6. Полученный текст саммари сохраняется как Summary для соответствующего окна сообщений; событие переходит в `completed`.

### Поток 3. Cumulative — ручной запуск через API

1. Клиент дергает существующий API ручного запуска cumulative-суммаризации (FT-005).
2. Создаётся cumulative-событие.
3. Дальнейшие шаги — идентичны шагам 3–6 потока 2. Используется **cumulative промпт**.

### Поток 4 (мейнтейнер). Изменение одного промпта

1. Мейнтейнер открывает артефакт нужного режима.
2. Правит его содержимое без чтения логики вызова LLM (CTR-01).
3. PR затрагивает только этот артефакт (опционально — обновлённые expectation-тесты, фиксирующие новое содержимое промпта в LLM-вход).
4. Артефакт второго режима остаётся побайтно прежним (CTR-04). Поведение второго режима не меняется.

## Verify

### Exit Criteria

- `EC-01` В репозитории присутствуют два различимых артефакта-промпта; их содержимое отличается; каждый из них доступен для рецензии без чтения логики вызова LLM.
- `EC-02` Автотест подтверждает: при суммаризации self-contained источника LLM-провайдер получил системный промпт, побайтно равный содержимому self-contained артефакта.
- `EC-03` Автотест подтверждает: при суммаризации cumulative источника LLM-провайдер получил системный промпт, побайтно равный содержимому cumulative артефакта.
- `EC-04` Автотест подтверждает: подмена содержимого одного из артефактов не меняет значение системного промпта, передаваемого LLM-провайдеру для второго режима.
- `EC-05` Регрессионный прогон существующих тестов FT-005 / FT-007 зелёный: атомарность, идемпотентность, lease-recovery, per-source due, graceful shutdown — не сломаны.
- `EC-06` Старая единая промпт-константа (общая для обоих режимов) удалена; «двойного» пути нет, dead-code нет.
- `EC-07` `make build && make test && make lint` зелёные.

### Acceptance Scenarios

- `SC-01` **Два разных артефакта существуют.** Дано: репозиторий после реализации FT-008. Когда: открываем артефакт self-contained и артефакт cumulative. Тогда: оба читаемы без обращения к коду вызова LLM; содержимое отличается; нет точки, где они склеиваются в одну строку до момента передачи в LLM-провайдер.
- `SC-02` **Self-contained источник → self-contained промпт.** Дано: self-contained источник и его пост в pending. Когда: Summary Worker обрабатывает событие с LLM-mock, фиксирующим переданный системный промпт. Тогда: зафиксированное значение системного промпта равно содержимому self-contained артефакта побайтно.
- `SC-03` **Cumulative источник → cumulative промпт.** Дано: cumulative источник с готовым окном и due-моментом «сейчас». Когда: per-source планировщик создаёт cumulative-событие, Summary Worker обрабатывает его с LLM-mock. Тогда: зафиксированное значение системного промпта равно содержимому cumulative артефакта побайтно.
- `SC-04` **Изоляция изменений.** Дано: два прогона, отличающихся только содержимым self-contained артефакта (в одном — текущее, в другом — изменённое). Когда: в обоих прогонах суммаризируется один и тот же cumulative источник. Тогда: значение системного промпта, переданного LLM-провайдеру, побайтно идентично в обоих прогонах.
- `SC-05` **Регрессия пайплайна.** Дано: существующие тесты FT-005 (атомарность, идемпотентность, ручной API-запуск) и FT-007 (параллелизм, multi-instance, lease-recovery, per-source due, graceful shutdown). Когда: прогон после реализации FT-008. Тогда: все сценарии остаются зелёными без правки их ассертов.

## Open Questions

Вопросы, ответы на которые относятся к Design-фазе (`implementation-plan.md`); фиксируются здесь как явный input для последующего этапа и не должны быть «закрыты по умолчанию» при имплементации.

- `OQ-01` **Форма артефакта-промпта.** Отдельный файл (`.md` / `.txt` / `.tmpl`), отдельная Go-константа в выделенном файле, embed через `go:embed`, либо иной механизм? Критерии выбора: рецензируемость без чтения окружающего кода (CTR-01), стабильность сборки (FM-02), отсутствие рантайм-зависимостей (ASM-03).
- `OQ-02` **Раскладка по слоям.** В каком из слоёв biz / data / service физически живут артефакты и где принимается решение «по режиму — такой-то промпт»? Базовая интуиция: артефакты — в data-слое (как вход LLM-провайдера); выбор — в biz-слое (как доменное правило). Финальное решение фиксирует implementation-plan, сверяясь с [architecture.md](../../domain/architecture.md).
- `OQ-03` **Где валидируется наличие/непустота артефактов.** Compile-time (например, через `go:embed` + проверка размера в `init`), startup-time (валидация при старте процесса), либо lazy (при первом вызове)? Решение должно гарантировать, что отсутствие/пустота артефакта не обнаруживается посреди обработки события (FM-02).
- `OQ-04` **Базовая редакция cumulative-промпта в этой итерации.** Стартовать с побайтной копии текущей единой константы (NS-10, эквивалентность по поведению на момент перехода) или сразу с минимальной нейтральной адаптацией к диалоговой структуре? Если копия — фиксируется как baseline для последующих правок; если адаптация — границы адаптации должны быть явно очерчены, чтобы FT-008 не превратился в content-change feature.
- `OQ-05` **Как именно фиксировать LLM-вход в тестах.** Через mock LLM-провайдера, через интерфейс перехвата на границе biz↔data, через fake-провайдер в testcontainers-стиле? Должен быть способ, не требующий сетевых вызовов и устойчивый к refactor вызова провайдера. Решение определяет конкретные сигнатуры моков в implementation-plan.
- `OQ-06` **Точка удаления старой единой промпт-константы.** Удаляется одной правкой вместе с введением двух новых артефактов, либо проходит фазу «оба пути сосуществуют» (что противоречит EC-06)? Базовая позиция feature-документа — удалить одной правкой, без переходного периода; implementation-plan обязан подтвердить выполнимость или явно эскалировать.
