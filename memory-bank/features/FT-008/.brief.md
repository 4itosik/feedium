
# FT-008: Summarization Prompts Split

## Problem

В FT-005 саммари для всех источников генерируется по единому системному промпту, который зашит в код как константа. Это создаёт два класса контента — самодостаточные посты (RSS, HTML, Telegram-каналы) и накопительные треды Telegram-групп — обслуживаемые одной и той же инструкцией, при том что структура входа у них принципиально разная: статья с одним автором против диалога нескольких участников.

Последствия бездействия:

- Любое изменение промпта является одновременно изменением для обоих режимов: невозможно уточнить инструкции для одного класса контента, не меняя поведение для второго.
- Текущий промпт не содержит инструкций по обработке диалоговой структуры (участники, реплики-якоря, развитие обсуждения), так как разрабатывался под формат одиночного поста; для cumulative-режима это закрывает путь к доработке без переписывания всего промпта.
- Промпт-константа в коде разработчика — единая точка решений; нет артефакта, который владельцы промптов могли бы рецензировать как самостоятельную сущность.

## Task

Разделить системный промпт суммаризации на два независимых артефакта — для режима self-contained и для режима cumulative — так, чтобы дальнейшие изменения каждого из них были изолированы.

1. При генерации саммари самодостаточного материала используется промпт, предназначенный для self-contained режима.
2. При генерации саммари накопительного материала используется промпт, предназначенный для cumulative режима.
3. Изменение одного промпта не требует и не вызывает изменения второго.
4. Промпты являются явными артефактами проекта (а не только литералом внутри функции вызова LLM); их содержимое можно отрецензировать как отдельную сущность, без чтения логики вызова LLM.

Конкретный механизм хранения промптов, способ выбора нужного промпта в коде, формат файла, изменения интерфейса LLM-провайдера и стратегия загрузки — задачи Design-фазы.

## Context

- FT-005 (AI Summarization) и FT-007 (event processing) находятся в `delivery_status: done`. Текущий промпт суммаризации — одна Go-константа в data-слое, общая для обоих режимов.
- Поводом для разделения служит начало работ над улучшением саммари тредов: единая константа в коде делает невозможным вносить изменения для cumulative-режима без одновременного изменения поведения self-contained.
- Доменная модель уже различает режимы обработки (BR-01, glossary): self-contained и cumulative; режим источника зафиксирован в FT-003 и известен бизнес-логике в момент вызова LLM.
- Эта задача — первый шаг в серии изменений промптов суммаризации; параметризация переменными источника, runtime-управление и эксперименты намеренно отложены и могут стать отдельными фичами после FT-008.
- Раскладка артефактов должна следовать границам слоёв biz/data/service, зафиксированным в [memory-bank/domain/architecture.md](memory-bank/domain/architecture.md).

## Users

- **Пользователь Feedium** — конечный потребитель саммари. После FT-008 саммари тредов и саммари постов могут эволюционировать независимо, без риска взаимной регрессии.
- **Мейнтейнер промптов** (разработчик / владелец промптов) — получает явный артефакт, который можно рецензировать в отрыве от кода вызова LLM.

## Scope

### In Scope

- Два независимых системных промпта суммаризации: один для self-contained режима, второй для cumulative режима.
- Выбор нужного промпта в момент генерации саммари определяется режимом обработки источника, заданным в FT-003 (BR-01).
- Сохранение функциональных свойств FT-005: атомарность создания поста и инициации суммаризации, идемпотентность повторной обработки, доступность ручного запуска cumulative через API.
- Автотесты согласно testing-policy проекта: подтверждают, что для каждого режима используется соответствующий промпт.

### Out of Scope

- Хранение промптов в БД и runtime-управление через API/CLI/UI.
- Версионирование промптов и сохранение «какой промпт использовался» в записи саммари.
- Hot-reload промптов без пересборки бинаря.
- A/B-эксперименты, метрики качества саммари, мониторинг регрессии качества.
- Параметризация и шаблонизация промптов переменными источника (имя канала, дата, тип) — отложено в следующую итерацию.
- Любые изменения пайплайна FT-005 / FT-007: outbox, ретраи, расписание cron, lifecycle Summary Worker.
- Замена или добавление LLM-провайдеров, изменение модели, изменение лимитов max_input_chars / max_window.
- Пользовательский интерфейс для отображения или редактирования промптов.

## Acceptance Criteria

- В репозитории существуют два различимых артефакта-промпта (по одному на режим), доступные для рецензии без чтения логики вызова LLM. Их содержимое отличается.
- При генерации саммари для self-contained источника LLM-провайдер получает промпт self-contained режима; для cumulative источника — промпт cumulative режима. Соответствие подтверждено автотестами.
- Изменение содержания одного промпта не требует изменений во втором и не влияет на поведение второго режима.
- Поведение FT-005 сохранено: self-contained суммаризация запускается атомарно после сохранения поста; cumulative — по крону и по ручному запросу через API; повторная обработка идемпотентна.
- Операции суммаризации покрыты автотестами согласно testing-policy проекта.
